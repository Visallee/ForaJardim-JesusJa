SEÇÃO A: Contexto da Linguagem

Introdução ao Ruby

Ruby é uma linguagem de programação dinâmica, interpretada e totalmente orientada a objetos, criada em 1995 por Yukihiro Matsumoto (Matz).

Filosofia de Projeto

  • Código escrito para humanos lerem, não apenas máquinas executarem
  • Deve ser divertido programar em Ruby
  • Foco em produtividade e legibilidade

Contexto Histórico

  • 2004: Surgimento do Ruby on Rails — revolucionou desenvolvimento web
  • Comunidade vibrante e colaborativa focada em boas práticas
  • Linguagem eleita entre as mais queridas por desenvolvedores

Paradigma: Orientação a Objetos Pura

Ruby: "Tudo é Objeto"

Diferente de Java e C++, em Ruby até tipos primitivos são objetos.

Exemplo Prático

# Em Ruby, inteiros são objetos
numero = 42
puts numero.class              # => Integer
puts numero.even?              # => true
puts numero.times { |i| puts i }  # imprime 0 a 41

# Strings são objetos
mensagem = "Ruby é incrível"
puts mensagem.upcase    # => "RUBY É INCRÍVEL"
puts mensagem.length   # => 15
Benefício: Experiência coerente — mesma lógica OO funciona uniformemente em todo o código.

Encapsulamento em Ruby

Modificadores de acesso controlam visibilidade de métodos:

  • public: Chamáveis de qualquer lugar (padrão)
  • private: Só dentro da mesma classe, sem receptor explícito
  • protected: Dentro da classe ou por subclasses

Exemplo

class Personagem
  public
  def exibir_informacoes
    puts "Personagem: #{@nome}"
  end

  private
  def calcular_vida_total
    @vida + 10
  end
end

Sistema de Tipagem: Dinâmica e Forte

Tipagem Dinâmica

Variáveis não têm tipos declarados — tipo é determinado em runtime. 

valor = 42        # Integer
valor = "texto"   # String
valor = [1, 2, 3]  # Array
valor = true      # TrueClass

Tipagem Forte

Sem conversão implícita perigosa entre tipos incompatíveis. 

# Ruby - Erro!
resultado = 5 + "10"  # TypeError

# Conversão explícita
resultado = 5 + "10".to_i  # => 15

Duck Typing

"Se grasna como um pato e anda como um pato, é um pato."

O que importa não é a classe de um objeto, mas se ele responde aos métodos esperados.

Exemplo

class Guerreiro
  def atacar; "ataca com espada!"; end
end

class Mago
  def atacar; "lança feitiço!"; end
end

def executar_combate(combatente)
  puts combatente.atacar
end

executar_combate(Guerreiro.new)  # Funciona!
executar_combate(Mago.new)      # Funciona!
Resultado: Código mais flexível e reutilizável sem herança explícita.

O Ecossistema Ruby: Rails

Ruby on Rails (2004)

Framework web que revolucionou o desenvolvimento, popularizando conceitos modernos.

Padrão MVC

  • Model: Lógica de dados e negócio
  • View: Interface de usuário
  • Controller: Orquestração entre Model e View

Duas Filosofias Centrais

Convention over Configuration (CoC): Rails assume convenções sensatas. Classe Personagem mapeia tabela personagens automaticamente.
Don't Repeat Yourself (DRY): Evita duplicação através de abstrações e gems reutilizáveis.

Gems: O Ecossistema de Bibliotecas

Ruby possui um ecossistema rico de bibliotecas (gems) gerenciadas por RubyGems.

Gems Populares

  • ActiveRecord: ORM padrão do Rails para acesso a banco de dados
  • Devise: Autenticação e gerenciamento de usuários
  • Pundit: Autorização e controle de permissões
  • RSpec: Framework de testes
  • Puma: Servidor web de alta performance
  • mysql2: Driver direto para MySQL

SEÇÃO B: Análise das Tecnologias

Camadas de Acesso a Dados

Em uma aplicação Rails, o acesso a dados é estratificado em 3 níveis de abstração:

O Espectro de Abstração

Máxima Abstração ←                    → Máximo Controle

    ORM           Query Builder        Raw Queries
(ActiveRecord)      (Arel)           (SQL Direto)
  • ORM: Camada de mais alta abstração — trabalhar com objetos Ruby
  • Query Builder: Nível intermediário — controle fino mantendo abstração
  • Raw Queries: Acesso direto — controle total, performance máxima

ORM: ActiveRecord

O Padrão Ouro do Rails

ActiveRecord é o ORM padrão desde 2004, mapeando tabelas em classes Ruby.

CRUD Automático

class Personagem < ApplicationRecord
end

personagem = Personagem.create(nome: "Arthos", nivel: 1)
personagem = Personagem.find(1)
personagem.update(nivel: 2)
personagem.destroy

Convenções Automáticas

Convenção Exemplo
Classe (singular) Personagem
Tabela (plural) personagens
Chave primária id
Timestamps created_at, updated_at

Relacionamentos no ActiveRecord

1:N (Um para Muitos)

class Personagem < ApplicationRecord
  has_many :itens
  has_many :missoes
end

class Item < ApplicationRecord
  belongs_to :personagem
end

N:N (Muitos para Muitos)

class Personagem < ApplicationRecord
  has_many :personagem_missoes
  has_many :missoes, through: :personagem_missoes
end

personagem = Personagem.find(1)
personagem.missoes              # Lista todas as missões
personagem.missoes << missao  # Adiciona missão

Queries com ActiveRecord

API Fluente

# SELECT e filtragem
Personagem.all
Personagem.where(nivel: 10)
Personagem.where("nivel > ?", 5)

# Ordenação e limite
Personagem.order(nome: :asc).limit(10)

# Joins e eager loading
Personagem.joins(:missoes)
Personagem.includes(:missoes)  # Evita N+1!

# Agregação
Personagem.count
Personagem.average(:nivel)
Personagem.maximum(:nivel)

ActiveRecord: Vantagens e Desvantagens

✅ Vantagens

  • Sem SQL explícito
  • Proteção SQL Injection automática
  • Portabilidade (MySQL, PostgreSQL, SQLite)
  • Associações automáticas
  • Migrações versionadas

❌ Desvantagens

  • SQL subótimo em queries complexas
  • Problema N+1 sem cuidado
  • Overhead de abstração
  • Curva aprendizado recursos avançados
  • Limitado para queries muito especializadas

Query Builder: Arel

Nível intermediário entre ORM e SQL puro. Oferece controle fino mantendo abstração.

Construção Programática

tabela = Personagem.arel_table

query = tabela
  .project(tabela[:nome], tabela[:nivel])
  .where(tabela[:nivel].gt(5))
  .order(tabela[:nome].asc)
  .limit(10)

Personagem.find_by_sql(query.to_sql)

Operadores Relacionais

tabela[:nivel].eq(10)          # = 10
tabela[:nivel].gt(5)          # > 5
tabela[:nome].matches('%Arthos%')  # LIKE
tabela[:nivel].in([1, 2, 3])    # IN

Raw Queries: Acesso Direto

SQL explícito sem abstração — controle total sobre banco.

Executar Raw Queries

# Método 1: Connection direta
connection = ActiveRecord::Base.connection
resultado = connection.execute("SELECT * FROM personagens WHERE nivel > 5")

# Método 2: Via find_by_sql (RECOMENDADO)
personagens = Personagem.find_by_sql(
  "SELECT * FROM personagens WHERE nivel > ? ORDER BY nome", [5]
)

# Método 3: CTE complexa
query = <<-SQL
  WITH personagens_ativos AS (
    SELECT id, nome FROM personagens WHERE ativo = 1
  )
  SELECT * FROM personagens_ativos
  WHERE created_at > NOW() - INTERVAL 7 DAY
SQL
⚠️ Cuidado: SQL Injection! Sempre parametrize com ?.

Comparação: ORM vs Query Builder vs Raw

Critério ORM (ActiveRecord) Query Builder (Arel) Raw Query (SQL)
Curva de aprendizado Baixa Média Alta
Performance Moderada Boa Excelente
SQL Injection Automática Automática Manual
Controle Baixo/Médio Médio/Alto Total
Portabilidade Alta Alta Baixa
Manutenibilidade Alta Média Média

SEÇÃO C: Comparação Crítica

Trade-offs Reais em Produção

Pergunta central: "O ActiveRecord perde muita performance comparado a SQL puro?"

Espectro de Abstração vs Controle

← Maior Abstração

ORM → Query Builder → Raw SQL

Maior Controle →

  • Esquerda: Melhor legibilidade, menos código, proteção automática — menor performance
  • Direita: Máximo controle e performance — código verboso, mais risco de erros

A Armadilha N+1 Queries

O Problema

# ❌ PROBLEMA: 1 query + N queries (101 total!)
personagens = Personagem.limit(10)
personagens.each do |p|
  puts p.itens.count  # Query por personagem!
end

A Solução: Eager Loading

# ✅ SOLUÇÃO: Apenas 2 queries!
personagens = Personagem.includes(:itens).limit(10)
personagens.each do |p|
  puts p.itens.count  # Sem query adicional!
end
Conclusão: O problema N+1 é a verdadeira armadilha, não o overhead do ORM. Uma única linha (.includes()) reduz 101 queries para 2!

Migrações Versionadas

O Conceito

Mudanças de esquema expressos como código Ruby versionado — não scripts SQL soltos.

Exemplo de Migração

class CreatePersonagens < ActiveRecord::Migration[8.1]
  def change
    create_table :personagens do |t|
      t.string  :nome,  null: false
      t.integer :nivel, default: 1
      t.timestamps
    end

    add_index :personagens, :nome, unique: true
  end
end

Comandos

rails db:migrate           # Executar migrações
rails db:rollback          # Desfazer última
rails db:migrate:status    # Verificar status

Benchmark: Análise de Performance

Cenário: Banco com 10.000 personagens e 100.000 itens, buscando 100 personagens com seus itens.

Resultados Práticos

N+1 (sem includes)
101 queries, 2500ms
ActiveRecord + includes
2 queries, 150ms ⭐
Query Builder (Arel)
1 query, 80ms
SQL Puro
1 query, 60ms
Descoberta-chave: Diferença entre ActiveRecord+includes e SQL puro é apenas ~25%. Muito menor que a diferença entre N+1 e includes (16x!).

7 Operações CRUD do Sistema RPG

Demonstração prática comparando SQL Puro vs ActiveRecord usando o projeto real.

Modelo de Dados do RPG

  • Personagem: id, nome, nivel, id_inventario_id, timestamps
  • Inventario: id, capacidade_maxima, euro, timestamps
  • Item: id, id_inventario_id, nome, tipo, raridade, peso, timestamps

Query 1: SELECT Simples

Buscar Todos os Personagens

Endpoint: GET /personagems

SQL Puro

SELECT id, nome, nivel, 
       id_inventario_id, created_at, updated_at
FROM personagens;

ActiveRecord

def index
  @personagems = Personagem.all
  render json: @personagems
end

Resultado da API

Query 2: SELECT com JOIN

Buscar Inventário com Itens (1:N)

Endpoint: GET /inventarios/1

SQL Puro

SELECT i.id, i.capacidade_maxima,
       it.id AS item_id, it.nome
FROM inventarios i
LEFT JOIN items it 
  ON i.id = it.id_inventario_id
WHERE i.id = 1;

ActiveRecord

def show
  @inventario = Inventario
    .includes(:items)
    .find(params[:id])
  render json: 
    @inventario.as_json(
      include: :items)
end

Status: 200 OK | Tempo: 178 ms | Tamanho: 1.08 KB

Vantagem ActiveRecord: JSON automaticamente aninhado. SQL puro retornaria linhas duplicadas.

Query 3: INSERT Simples

Criar Novo Personagem

Endpoint: POST /personagems

SQL Puro

INSERT INTO personagens

ActiveRecord

def create
  @p = Personagem.new(p_params)
  if @p.save

  end
end

Vantagens: Validações automáticas, timestamps gerenciados, whitelist de parâmetros.

Boas Práticas Recomendadas

1. Eager Loading — Evitar N+1

# ❌ Errado
Personagem.all.each { |p| p.itens.count }

# ✅ Correto
Personagem.includes(:itens).all

2. Validações Robustas

class Personagem < ApplicationRecord
  validates :nome, presence: true
  validates :nivel, numericality: { 
    only_integer: true, greater_than: 0 
  }
end

3. Scopes para Queries Comuns

scope :ativo, -> { where(ativo: true) }
scope :nivel_alto, -> { where("nivel >= ?", 10) }

# Uso
Personagem.ativo.nivel_alto

4. Migrações para Todas Mudanças

Sempre versione mudanças de schema com migrações, nunca SQL solto.

CONCLUSÃO

Descobertas-Chave

  • ActiveRecord com .includes() oferece performance apenas ~25% mais lenta que SQL puro
  • Problema N+1 é a armadilha real — 16x mais lento que includes
  • Desenvolvimento 10-20x mais rápido com ORM vs SQL puro
  • Migrações versionadas oferecem manutenibilidade massiva de longo prazo
  • Relacionamentos declarativos tornam código muito mais claro

Recomendação para Projeto RPG

Use ActiveRecord como padrão, aplicando:
  • ✅ Eager loading com .includes()
  • ✅ Índices apropriados no banco
  • ✅ Validações robustas no model
  • ✅ Migrações para todas mudanças
  • ✅ SQL puro apenas em casos excepcionais

Essa abordagem oferece melhor equilíbrio entre velocidade de desenvolvimento, manutenibilidade e performance adequada para evolução futura.
